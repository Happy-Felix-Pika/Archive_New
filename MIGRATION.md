# Переведення бойового архіву на нову версію

Інструкція для справжнього архіву з реальними даними. На тестовій базі ти
все це вже проходив — тут те саме, але одним скриптом і з захистом від помилок.

Орієнтовний час: 15–30 хвилин, більшу частину з них — очікування.

---

## Що в архіві

```
archive/
├── MIGRATION.md               ← ця інструкція
├── APP_DEVELOPMENT_GUIDE.md   ← як писати застосунки
├── migrate_production.py      ← скрипт переведення бази
├── main.py                    ← запуск архіву
├── Dockerfile
├── requirements.txt
├── furry_archiver.py          ← УЖЕ ПЕРЕРОБЛЕНИЙ архіватор
├── dashboard.html
├── core/                      ← ядро
├── blueprints/                ← розділи ядра
├── static/                    ← dashboard.js, apps.js, dashboard.css
├── migrations/                ← SQL-міграції (скрипт бере їх звідси)
└── apps/installed/
    ├── furry/                 ← автори, серії, запуск архіватора
    ├── online/                ← вкладка «Онлайн» (механізм перегляду)
    ├── e621/                  ← джерело e621 для «Онлайн»
    ├── inkbunny/              ← джерело Inkbunny для «Онлайн»
    ├── duplicates/            ← пошук дублікатів
    └── chat/                  ← чат
```

**Твоє, чого в архіві немає і що треба взяти зі старого проєкту:**

- `archiver_config.json` — налаштування бази, сховища, e621, Inkbunny

Теку `live_sources/` зі старого проєкту брати **не треба**: джерела e621 і
Inkbunny тепер окремі застосунки в `apps/installed/`.

**Важливо:** `furry_archiver.py` бери з архіву, а не зі старого проєкту. У
архіві — перероблена версія, яка пише в нові таблиці. Старий після переходу
працювати не буде.

---

## Крок 1. Бекап

phpMyAdmin → вибери **бойову** базу → вкладка **Експорт** → **Вперед**.
Скачається `.sql` з усією базою. Перевір, що файл не порожній.

Без цього кроку далі не йди. Після кроку 5 скрипта шляху назад без бекапу немає.

---

## Крок 2. Зупинити архів

Portainer → Containers → контейнер архіву → **Stop**.

Навіщо: поки архів працює, архіватор може писати в базу посеред переведення.

---

## Крок 3. Покласти новий код

1. Скопіюй куди-небудь старий проєкт повністю — це твій шлях назад у разі чого.
2. Розпакуй архів.
3. Поклади в нього свій `archiver_config.json`.

Якщо архів збирається з Dockerfile — новий Dockerfile вже є в архіві, він
копіює і `apps/`, і `migrations/`. Старий цього не робив.

---

## Крок 4. Перевести базу

Скрипт один, запускається одним рядком. Є два способи — вибери зручніший.

### Спосіб А — зі свого комп'ютера (простіше)

Потрібен Python і бібліотека:
```
pip install pymysql
```

У `archiver_config.json` має бути секція `database` з адресою бойової бази, яку
видно з твого комп'ютера (не `localhost` контейнера, а реальна адреса сервера).

З теки проєкту:
```
python migrate_production.py
```

### Спосіб Б — усередині контейнера

Спершу збери й запусти контейнер з новим кодом (Portainer → оновити stack/
образ), потім Portainer → контейнер → **Console** → Connect:
```
python migrate_production.py
```

Налаштування бази скрипт візьме з тих самих змінних оточення
(`DB_HOST`, `DB_USER`, `DB_PASSWORD`, `DB_NAME`), що й архів.

> Увага: у способі Б контейнер уже запущено, і архів може встигнути
> стартувати на старій базі. Нічого не зламається — просто в консолі будуть
> помилки, поки скрипт не допрацює. Після нього перезапусти контейнер.

### Що скаже скрипт

Він двічі спитає підтвердження — відповідай `так`:

1. на початку: «це правильна база, архів зупинено, бекап зроблено?»
2. перед видаленням старої таблиці

Нормальний вивід виглядає так:

```
1. Стан бази
  ✓ стара схема — переводимо
2. Нові таблиці й копіювання даних
  ✓ записів у старій таблиці: 18342
  ✓ files:       18342
  ✓ furry_posts: 18342
3. Звірка даних
  ✓ нічого не загублено
  ✓ прив'язка до авторів перенесена повністю
  ✓ усі шляхи до файлів правильні
4. Зовнішні ключі — з downloads на files
  ✓ знято старий ключ ...
5. Прибирання старої таблиці — ЄДИНИЙ НЕЗВОРОТНИЙ КРОК
  ✓ усе зійшлось, дублікатів шляхів немає
  Видалити стару таблицю downloads? Бекап зроблено? [так/ні]: так
  ✓ стару таблицю видалено
6. Фонові задачі й застосунки
 ✓ ГОТОВО
```

Імена зовнішніх ключів скрипт знаходить сам — те, з чим ти бився в
phpMyAdmin на тестовій базі, тепер робити не треба.

---

## Крок 5. Запустити архів

Portainer → контейнер → **Start** (або `python main.py`).

У консолі при старті мають бути рядки:
```
  ✓ Застосунок 'chat' v1.0.0
  ✓ Застосунок 'furry' v1.0.0
  ✓ Застосунок 'online' v1.0.0
  ✓ Застосунок 'duplicates' v1.1.0
  ✓ Застосунок 'e621' v1.0.0
  ✓ Застосунок 'inkbunny' v1.0.0
```

Якщо поруч із застосунком ⚠ і текст помилки — архів усе одно працює, але цей
застосунок не завантажився. Покажи текст.

---

## Крок 6. Перевірка

Відкрий архів у браузері й пройдися:

1. **Внизу ліворуч** — «MariaDB online», зелена крапка.
2. **Огляд** — кількість файлів така сама, як була до переходу.
3. **Арти** — картинки відкриваються, відео перемотується, у картці є автор.
4. **Автори** — список на місці, у кожного правильна кількість файлів.
5. **Серія (pool)** — комікс гортається по порядку, «стор. N з M».
6. **Каталог** — теки гортаються, файл скачується.
7. **Конфіг** — є секції E621 і Inkbunny, паролі показано як «збережено».
8. **Завантажити файл** з кирилицею в назві — завантажився, відкривається.
   Спробуй і без автора, вказавши теку (напр. `Документи`), і не картинку, а
   PDF — він з'явиться в каталозі.
9. **Видалити** щойно завантажений — зник із галереї й з'явився в «Кошику».
   Натисни «Відновити» — повернувся на місце з тегами. Видали знову й
   «Видалити назавжди» — зник і з кошика.
10. **Запуск** — скачати автора з серією. Потім перевір у phpMyAdmin:

```sql
SELECT f.rel_path, fp.subfolder
FROM files f JOIN furry_posts fp ON fp.file_id = f.id
WHERE fp.subfolder IS NOT NULL
ORDER BY f.id DESC LIMIT 10;
```

   Назва теки в `rel_path` має збігатися з `subfolder`. Потім відкрий ці файли
   в галереї.

11. **Застосунки** — шість штук, усі «увімкнено». Вимкни e621 і перезапусти:
    у «Онлайн» має лишитись тільки Inkbunny. Увімкни назад.
12. **Консоль браузера (F12)** — без червоних помилок.

**Якщо користуєшся Nextcloud** — пункти 3, 6, 8, 9 і 10 обов'язково саме в
режимі Nextcloud. Цю частину я не мав на чому перевірити.

## Якщо щось пішло не так

### Скрипт зупинився з ✗ до кроку 5

Нічого не видалено, стара таблиця ціла, архів можна запускати на старому коді.
Скопіюй увесь вивід скрипта й покажи.

Найчастіша причина — **два записи з однаковим шляхом до файлу**. Скрипт
покаже, які саме. Знайти всі:

```sql
SELECT a.folder_name, d.subfolder, d.filename, COUNT(*) AS копій,
       GROUP_CONCAT(d.id) AS id
FROM downloads d JOIN artists a ON a.id = d.artist_id
GROUP BY a.folder_name, d.subfolder, d.filename
HAVING копій > 1;
```

Зазвичай це той самий файл, записаний двічі. Залиш один запис, решту видали
(`DELETE FROM downloads WHERE id IN (...)`) і запусти скрипт знову — він
продовжить з того місця, де зупинився.

### Скрипт упав посередині з помилкою Python

Запусти ще раз. Кроки до видалення старої таблиці повторюються без шкоди.

### Архів запустився, але щось не працює

1. Зупини архів.
2. Покажи помилку з консолі сервера і з консолі браузера (F12).

### Повний відкат

Якщо треба повернути все як було:

1. Зупини архів.
2. phpMyAdmin → бойова база → **Імпорт** → твій бекап з кроку 1.
3. Поверни старий проєкт з копії, зробленої на кроці 3.
4. Запусти.

## Що змінилось для тебе в роботі

- У меню новий розділ **«Застосунки»** — там можна вимкнути furry, дублікати,
  чат, «Онлайн», або окремо e621 чи Inkbunny. Вимкнення діє після перезапуску.
  e621 і Inkbunny залежать від «Онлайн»: поки вони увімкнені, «Онлайн»
  вимкнути не дасть.
- У **«На перевірку» → «Дублікати»** — кнопка **«Шукати по всьому архіву»**:
  знаходить однакові файли в різних авторів.
- У картці файлу — кнопка **🔓**: відкрити окремий файл з прихованої теки для
  зовнішнього ключа.
- **Кошик.** Видалений файл не зникає, а йде в розділ «Кошик». Звідти його
  можна повернути на старе місце разом із тегами, автором і улюбленим — або
  прибрати назавжди. Фізично файли лежать у прихованій теці `.trash`
  усередині сховища: так вони не загубляться при оновленні контейнера.
  Якщо на старому місці вже з'явився інший файл, відновлення його не
  затре, а попросить спершу прибрати.
- **Завантаження без автора.** Автор тепер необов'язковий: без нього файл
  іде у вказану теку або в корінь. Приймається будь-який файл — документи,
  музика тощо; у «Артах» показуються, як і раніше, лише зображення й відео,
  решта — у «Каталозі».
- **Дублікати в локальному режимі.** «Зберегти новий» і «Замінити старий»
  раніше працювали тільки з Nextcloud. Тепер — з будь-яким сховищем, а
  замінений файл іде в кошик.
- **Назва архіву** задається в «Конфіг → Загальне». За замовчуванням — «Archive».
- Кожен запуск архіватора, включно з нічним авто-оновленням, тепер лишає
  запис. Переглянути: `адреса-архіву/api/jobs`.
